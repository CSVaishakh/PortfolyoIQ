# PortfolioIQ rebuilding plan

## Purpose and current state

This plan continues the federated-rebalancing work on branch `rebuild-codex`
after commits `661b9c6` and `9d349b9`.

Those commits correctly address several structural defects in the original
pipeline: raw feature scale dominance, a time-only label veto, index-correlated
synthetic days, single-sample local overfitting, uniform/racing FedAvg, and
missing sample counts.

They do **not** yet make the product a suitable or trustworthy portfolio
rebalancing engine. The principal gap is that the current federated model is
trained on labels generated by its own heuristic. It can reproduce that
heuristic, but it cannot learn whether rebalancing was economically beneficial.

## Independent expert findings

Severity definitions:

- **Critical**: could produce unsafe/misleading advice, compromise a global
  model, or prevent a correct deployment.
- **High**: materially weakens validity, reliability, security, or operations.
- **Medium**: important improvement, but not a release blocker by itself.

## Critical issues to resolve first

1. **Secure aggregation endpoints.** Require server-side administrator
   authorization for aggregation, or remove the public aggregate route. Do not
   rely on a browser-exposed long-lived admin secret.
2. **Enforce one feature contract.** Remove raw `/train`, or make it internal,
   authenticated, shape-validated, finite-value-validated, and standardized
   exactly once through the canonical feature/scaler specification.
3. **Use target-relative portfolio logic.** Collect target allocation and
   calculate active weights as `current weight - target weight`; equal weight
   must never be an implicit investment policy.
4. **Use economics as the primary decision.** Rebalance only where expected
   risk reduction over the relevant horizon exceeds brokerage, taxes, spread,
   market impact, and other implementation costs.
5. **Use outcome-based labels.** Replace heuristic labels with labels produced
   from a forward, net-of-cost backtest and, later, opt-in realised outcomes.
6. **Make data freshness explicit.** Validate pricing/market-data provenance
   and age. Do not issue a live recommendation when data are stale or missing.
7. **Prove setup and migration.** Apply and test database migration
   `0001_add_n_samples.sql` in a clean environment before deploying.

## Recommended architecture

```text
Portfolio + investor mandate + target allocation + tax/cost inputs
  -> validated current security and market data
  -> deterministic target-relative rebalance economics engine
  -> recommendation, trade list, cost, uncertainty, and rationale

Historical replay / opt-in realised outcomes
  -> versioned feature and label pipeline
  -> calibrated secondary ML model
  -> protected, versioned federated aggregation
  -> monitoring, rollback, and audit trail
```

### Design rules

- Generate one shared `FeatureSpec` containing feature order, units, scaler,
  label version, and model version. Both TypeScript and Python must consume the
  same generated artifact instead of copying constants manually.
- Store model metadata with every update: model/scaler/feature/label versions,
  participant eligibility, validation metric, round ID, source-data range, and
  rollback parent.
- Serialize aggregation with a job/round table, database transaction/locking,
  and an outbox/retry step. Mark a model active only once the model service has
  confirmed the update.
- Add update clipping, influence caps, rate limiting, and quality thresholds.
  Be precise about privacy: sharing ordinary weights is not secure aggregation.
- Present results as educational decision support until suitability, market-data
  governance, and model-validation requirements are satisfied.

## Phased roadmap

### P0 — complete setup and make the current pipeline safe

1. Review and commit intended WIP; preserve all other branches and the stash.
2. Apply migrations through the controlled migration command on a clean
   database. Verify schema, seed data, and rollback/recovery procedure.
3. Require authorization on `/model/aggregate`; restrict model-service access
   to the platform service.
4. Disable or repair raw `/train` so every model always uses the canonical
   standardized feature space.
5. Add explicit model/scaler/feature versions to stored global and user weight
   snapshots; reject incompatible uploads.
6. Correct README, admin UI, endpoint documentation, dataset counts, and the
   actual training/aggregation flow.

#### P0 acceptance criteria

- A clean machine can run database migration, platform service, model service,
  and client using documented commands.
- A non-admin cannot aggregate, seed, or mutate global model state.
- Raw, wrong-width, non-finite, wrong-version, and single-class model uploads
  are rejected predictably.
- No code path can generate or aggregate weights trained in a different feature
  scale from the seeded model.

### P1 — make the rebalancing decision financially valid

1. Extend the template/intake with target weight, cash, account type, tax-lot
   data where applicable, investor horizon, risk preference, and constraints.
2. Implement target-relative drift, cash-aware trade generation, minimum trade
   sizes, turnover limits, and no-trade bands.
3. Model Indian implementation costs and tax consequences transparently;
   distinguish estimates from verified broker/tax calculations.
4. Replace static generic market data with a governed source, provenance, and
   a freshness service-level objective. Provide an explicit unavailable/stale
   result state.
5. Add known portfolio test cases approved against documented investment-policy
   rules.

#### P1 acceptance criteria

- Two portfolios with identical holdings but different targets can legitimately
  receive different recommendations.
- Every trade list reconciles to cash and target weights.
- The UI shows the estimated benefit, implementation cost, tax impact,
  uncertainty, and reason for a hold/rebalance decision.
- Stale or incomplete prices block a live recommendation rather than silently
  using old data.

### P2 — make ML scientifically defensible

1. Generate labels from forward, net-of-cost economic results; do not train on
   the same rules used to produce the displayed recommendation.
2. Build reproducible dataset generation with provenance, fixed seeds where
   appropriate, and generated feature/scaler artifacts.
3. Use chronological train/validation/test splits and report calibration,
   precision/recall, AUC where appropriate, baseline comparison, and regime
   performance.
4. Compare against simple baselines: no-trade band, deterministic economic
   rule, and a non-federated validated model.
5. Define promotion gates for a global model, including minimum validation
   quality and no regression in important market regimes.

#### P2 acceptance criteria

- Test data are strictly unavailable to the label-generation/training process.
- The ML model demonstrates incremental value over the deterministic economics
  baseline, or is not used in production recommendations.
- Reported confidence is calibrated and described as model confidence, not
  investment certainty.

### P3 — harden federated learning and operations

1. Add explicit aggregation rounds, eligibility rules, update clipping,
   participant rate limits, influence caps, and model-quality checks.
2. Add audit logs, dashboards, rollback, alerting, and a kill switch for model
   activation.
3. Collect opt-in outcome feedback only with a documented privacy policy and
   retention/consent controls.
4. Evaluate whether federated learning provides measurable value. A centrally
   validated model plus deterministic rebalancing economics may be safer for a
   small retail product.

#### P3 acceptance criteria

- Repeated or concurrent aggregation requests cannot create inconsistent active
  model state.
- A single account or a small Sybil set cannot dominate an aggregation round.
- Operators can identify, disable, and roll back a model version with a complete
  audit trail.

## Required automated tests

1. TypeScript/Python scaler parity using fixed known vectors.
2. TypeScript/Python prediction parity for a canonical weight vector.
3. API tests for authentication, authorization, malformed data, non-finite
   values, invalid feature/model versions, and invalid sample counts.
4. Deterministic weighted-FedAvg tests using different sample counts.
5. Concurrent aggregation and model-service failure/retry tests.
6. Database migration test from the pre-`n_samples` schema.
7. End-to-end workflow: seed -> two eligible clients contribute -> aggregate ->
   activate a versioned global model -> client retrieves compatible weights.
8. Financial decision tests: target drift, no-trade band, taxes, transaction
   costs, cash reconciliation, stale data, and missing mandate inputs.
